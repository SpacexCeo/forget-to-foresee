# Technical depth and code quality: how judges score it (C3)

Research cycle 4, 2026-11-08 22:05 UTC. Search-result snippets were read, not full pages, unless marked. Moderate depth.

## Findings
1. **Hackathon rubrics define "technical complexity" as sophistication of the codebase, back end as well designed as
   the front end, and code smells or likely security holes.** No surveyed rubric names tests explicitly; several
   say messy code is not penalised and complexity is "not the key metric".
   - https://dod.ngo/blog/2018/our-judging-process (read 2026-11-08): judges look for code smells and likely
     security holes.
   - https://swecc.notion.site/Judging-Criteria-eabbc4b4287d43e5a2b41887f859814b (2026-11-08): "Technical Depth".
   - https://libguides.library.nd.edu/hesburgh-hackathon/judging (2026-11-08): back end as complex and well
     designed as the front end.
   - https://www.hackerearth.com/challenges/hackathon/american-express-makeathon-2024/custom-tab/evaluation-criteria/
     (2026-11-08): code quality, technology, architecture as separate parameters.
   - https://beincrypto.com/wchl-2025-national-round-judges-takeaways (2026-11-08): Web3 judges agreed complexity
     is not the key metric (a crypto-hackathon counterweight).
   Consequence: depth earns points only when a judge can see it in minutes; tests count as evidence of "works",
   not as a separate score. That supports keeping C3 at 13 and moving test evidence into C1.
2. **NEAR's own contract security checklist** (https://docs.near.org/smart-contracts/security/checklist, 2026-11-08)
   is the reference a technical juror for a NEAR hackathon reaches for: state changes in callbacks rather than before
   cross-contract calls, re-run after any security-sensitive change. Best practices
   (https://docs.near.org/smart-contracts/anatomy/best-practices, 2026-11-08): overflow checks enabled, `require!`
   early, `log!` for events, efficient account-ID storage, reuse near-sdk re-exports. Third-party audit checklist:
   https://docs.hacken.io/checklists/near-checklist (2026-11-08): `#[init]` present, suitable collection types,
   near-sdk up to date.
3. **Contract testing norm:** integration tests in near-workspaces (Rust or JS) against a local sandbox, same tests
   runnable on testnet (https://github.com/near/near-workspaces-rs, https://docs.near.org/sdk/rust/testing/integration-tests,
   2026-11-08). A contract with unit tests only reads as "one layer is scaffolding". One third-party skill doc says
   near-api-rs replaces workspaces for tests; unverified against the official docs.
4. **Determinism and parity evidence** that technical readers recognise: replay the same recording twice and
   compare state hashes (https://docs.rs/crate/tickwise/0.1.0); record in the reference, replay through the
   rewrite headlessly and report the first divergence (https://www.mintlify.com/banteg/crimson/reverse-engineering/runtime/differential-testing);
   CI replays on several platforms and compares checksums (https://bugnet.io/blog/how-to-debug-desync-in-deterministic-lockstep-games).
   All 2026-11-08, secondary sources. This maps directly onto our `baseline-2d-1` parity rule with `prototype-2d/`.

## Checklist for C3 (ten items, one point each, scaled to 10)
1. Architecture fits on one page (README diagram or `docs/`) and matches the code tree.
2. `npm test` green from a clean clone, with the count and runtime stated.
3. Parity tests: the same seed and inputs give bit-identical state in the engine and the reference; a state hash
   per turn or per season is printed somewhere a judge can see.
4. Tamper test: altering one committed trial or shard is detected by the verifier (test exists and runs).
5. Contract has integration tests (near-workspaces sandbox or testnet), not unit tests only.
6. Contract passes the NEAR security checklist items that apply: `#[init]`, overflow checks, `require!` with
   messages, no state change before a cross-contract call, access control on the commit method.
7. Contract test vectors are generated by the same engine as the game (one source of truth).
8. Agent rules live in one readable module; agents are deterministic under a seed.
9. No dead or mock code presented as a feature (cross-check README's real/mock table).
10. A performance figure (frame time or turn latency) against a stated budget.
Cap: if a judge cannot find items 1 to 3 within five minutes, C3 is capped at 6 regardless of real depth.
